# 尼康 Z6 固件开发手册

> 版本：2026-10-29 · 对应固件 Z6 C 3.80（`Z_6_0380.bin`）
> 面向对象：接手这份工作的后来者。只读本文 + 仓库脚本即可复现全流程。
> 用途限定：互操作性研究与个人学习。请勿再分发固件内容或派生模块。

---

## 0. 五分钟看懂这是什么

`Z_6_0380.bin` 是一个 **34,923,366 字节**的加密容器。解开之后是四个独立程序，其中最大的是
**Engine（约 33.5 MB 的 ARM Thumb-2 代码）**，跑在一个名为 **µT-Kernel** 的实时系统上，
主处理器是 **ARM926**。

整个工程的三个关键事实：

1. **加密是位置无关的异或**，密钥可由多个机型的固件交叉推出——不需要破解密码学。
2. **补丁可以只改 EG 一个模块**，用等长字节替换；整包签名（`SHA1(body‖K8)`）因此被绕开。
3. **风险不在解密，在投递**：相机是否接受独立 EG 模块、失败后能否恢复，都还没有人验证过。

## 1. 快速开始

```powershell
$py = 'python'   # Python 3.10+，需要 numpy

& $py -m z6fw info       # 读出 stock EG、模块清单、可用预设与目标尺寸
& $py -m z6fw selftest   # 零改动重打包，必须与输入字节一致
& $py -m z6fw probe      # 生成 CRC 故意损坏的通道探路文件
& $py -m z6fw aspect --preset aspect-21x9
```

前置依赖：`Z_6_0380.bin`（官方原件）与 `_repo/key.json`（三张 XOR 表）。
`key.json` 由 `_repo/nikon-fw-key-tool-main/extract_key.py` 生成，见第 4 章。

产物落在 `build/`，每个 `.BIN` 旁边有一份同名 `.json` 报告，记录每处改动的偏移、原字节、新字节。

## 2. 固件格式

### 2.1 三层结构

```
文件（Z_6_0380.bin，34,923,366 B）
├─ 0x0000  32 B 明文头：[20 B SHA-1 摘要][12 B 未识别]
├─ 0x0020  32 B 明文标签：32 个 ASCII 空格
└─ 0x0040  起为 body（加密）
   ├─ body 0x00   32 空格（与文件 0x20 重合，即标签本身）
   ├─ body 0x20   BE32 模块数 | BE32 目录大小 | 8 字节零
   ├─ body 0x30   N × [16 B 名字][BE32 偏移][BE32 长度][8 B 零]
   ├─ 模块区（每个模块尾部 2 B CRC）
   └─ 尾部 16 B：BE16 包 CRC + 14 B 零
```

实测：模块数 4，目录大小 176 = `48 + 32×4` ✓。

### 2.2 校验和

| 级别 | 算法 | 覆盖范围 |
|---|---|---|
| 模块 CRC | CRC-16/CCITT，多项式 `0x1021`，初值 0，不反转，无终值异或 | 模块 payload，存于模块末 2 字节（大端） |
| 包 CRC | 同上 | body 除最后 16 字节，存于尾部前 2 字节（大端） |

重要性质：**`CRC16(payload ‖ CRC) == 0`**。所以任何合法模块整体算 CRC 都是 0——
`z6fw` 全程用这个不变量自检。

### 2.3 scatter 描述符（模块偏移 0x14000）

模块不是单段直载，而是带初始化数据搬移表。Z6 3.80 实测 4 条描述符：

| # | ROM 源 | RAM 目标 | 长度 |
|---|---|---|---|
| 0 | `0x11E94DD4` | `0xC1800000` | `0x00101400`（1 MiB） |
| 1 | `0x11F96200` | `0xC2A10000` | `0x00000FF8` |
| 2 | `0x11F97200` | `0xC9200000` | `0x0007C478` |
| 3 | `0x11E94DD4` | `0x04008FE0` | `0x00000020` |

第 4 个字固定为 `BASE + 0x6C = 0x1002006C`，**这是判断模块基址是否正确的指纹**：
拿任意一份尼康 Z 系 EG 模块，读偏移 `0x14000` 的第 4 个 32 位字，等于 `BASE+0x6C` 即基址正确。

### 2.4 加载基址

```
BASE = 0x10020000
```

Z30（EXPEED 6，C 1.20）与 Z6（C 3.80）**基址相同**，scatter 表位置也相同。
这一条让跨机型映射成为可能。

## 3. 加密方案

### 3.1 算法

```
plain[0x20 + i] = cipher[0x20 + i] XOR T1[i & 0xFF]
                                    XOR T2[(i >> 8) & 0xFF]
                                    XOR T3[(i >> 16) & 0xFF]      （i ≥ 0x20，i 为 body 偏移）
```

- T1/T2/T3 各 256 字节；keystream 周期 **2²⁴ = 16 MiB**；
- 头部（0x00–0x1F）与空格标签（0x20–0x3F）不加密；
- 加密与解密是同一个操作。

### 3.2 为什么熵是 8.0 却"有规律"

这是本项目早期最容易走偏的地方。三类现象都有简单解释：

| 现象 | 原因 |
|---|---|
| 全文件熵 ≈ 8.0、无任何字符串 | keystream 均匀，把明文统计特性抹平了 |
| 某些 64 KiB 窗口字节计数**比随机还均匀**（chi²≈10） | padding 区密文就是 `T1 ^ 常数`，而 T1 近似 0..255 的置换 |
| 同一 64 字节片段出现数十次且都落在 `mod 256` 同一残基 | 同上，padding 以 256 为周期重复 |
| 相邻字节相等概率比随机低约 20% | T1 表内相邻项很少相等 |

**结论：高熵不等于强加密。** 判断是否"扩散型加密"，看的是**跨版本同一位置是否大量相同**，
而不是熵。

### 3.3 密钥恢复所需样本

`extract_key.py` 从"常量填充的 padding 扇区"反推三张表，需要覆盖全部 256 个 T3 块。
本次实际用到 **8 个镜像**（比文档给的最少 4 个更宽松）：

```
Z_6_0380.bin  Z_6_0370.bin  Z_7_0380.bin  Z_8_0311.bin
Z_50_0251.bin Z7_2_0162.bin Z_5_0143.bin  Z_30_0111.bin
```

覆盖进度：3 个 → 131/256；加 Z8/Z50/Z7II → 254/256（缺 125、193）；再加 Z5/Z30 → 全覆盖。

**校验证据**：8 个镜像共 **30 个模块 CRC + 8 个包 CRC** 全部通过，三张表的自检哈希一致。
这不是"解出乱码"，是密钥正确。

所有地址为 ARM 运行时地址，减 `BASE` 得模块偏移。置信度：✅ 实测 / 🔎 结构推断 / ⚠️ 未闭合。

| 模块基址 | `0x10020000` | ✅ | scatter 第 4 字验证 |

| **出图尺寸表** | `0x1065FDD0` | ✅ | 12 条 × 6 B = `(u16 w, u16 h, u16 aspect_id)` |
| 尺寸表读取点 | 字面量 `0x103C3464` | ✅ | 全模块唯一引用 |

| 第二尺寸表 | `0x1152A130` | 🔎 | 步长 4 的 `(w,h)` 表，引用在 `0x11F677A8`（.data 区） |
| 裁切几何 | `0x103C2FB8`–`0x103C3460` | ⚠️ | **由代码计算，非字面量表**，见 5.2 |

### 5.1 出图尺寸表结构（✅ 实测）

```
偏移(模块)   宽    高    aspect_id    含义
0x63FDD0   6048  4024      0         FX  L (3:2)
0x63FDD6   4528  3016      0         FX  M
0x63FDDC   3024  2016      0         FX  S
0x63FDE2   4016  4016      3         1:1 L
0x63FDE8   3008  3008      3         1:1 M
0x63FDEE   2000  2000      3         1:1 S
0x63FDF4   3936  2624      0         DX  L (3:2)
0x63FDFA   2944  1968      0         DX  M
0x63FE00   1968  1312      0         DX  S
0x63FE06   6048  3400      4         16:9 L
0x63FE0C   4528  2544      4         16:9 M
0x63FE12   3024  1696      4         16:9 S
0x63FE18   3840  2160      4         4K 视频
0x63FE1E   1920  1080      4         1080p
```

`aspect_id`：`0` = 3:2（FX/DX 共用）、`3` = 1:1、`4` = 16:9。`1`、`2` 在本表中未使用。

### 5.2 裁切窗口为什么找不到（⚠️ 关键结论）

反编译 `0x103C2FB8` 段得到：

```c
psVar3 = (short *)(*in_r2 + (short)in_r2[10] * 0x14);   // 步长 0x14 的表，含 (w,h)
sVar1  = in_r2[1]            - *psVar3      / 2;        // x = 中心 - w/2
sVar2  = *(short*)(in_r2+6)  - psVar3[1]    / 2;        // y = 中心 - h/2
// 矩形 = (x, y) .. (x+w-1, y+h-1)
```

即裁切框是**从画面中心按表里尺寸算出来的**。但搜索"原始窗口"字面量全部落空：

```
(0, 312, 6048, 3400)      → 0 命中
(312, 3400)               → 0 命中
(1012, 0, 4024, 4024)     → 0 命中
(1056, 700, 3936, 2624)   → 0 命中
```

对比之下，出图尺寸表本身逐字存在。**因此传感器读取窗口由代码推导，不在表里。**

**后果**：只改尺寸表不改窗口，相机会把现有 16:9 窗口**重采样**到新高度——画面被压扁，不是裁切。
这正是上游 Z30 项目 v2 版本踩过的坑（"机内预览被纵向拉长"，v8 的"成片成功"结论后来被复测推翻）。

**下一步该做什么**：从 `0x103C2FB8` 段完整反编译，找到把 aspect 选择映射为窗口的那段代码，
再决定是改常量还是挂钩子。这是 21:9 项目的唯一阻断项。

## 7. 补丁方法论

### 7.1 六条硬约束（工具强制执行）

| # | 约束 | 违反后果 |
|---|---|---|
| 1 | 源 SHA-256 匹配 | 拒绝 |
| 2 | 源 CRC residue = 0 | 拒绝 |
| 3 | **改动必须等长** | 拒绝 |
| 4 | **必须匹配 expected 原字节** | 拒绝（这是防"改错位置"的核心） |
| 5 | 不得重叠、不得越过 payload 边界 | 拒绝 |
| 6 | 追加代码 4 字节对齐且不超容量 | 拒绝 |

输出前重算 2 字节 CRC 并自检 residue = 0。

### 7.2 三种补丁形态

- **A. 数据表项**（最简单）：等长改几个字节，如本项目的画幅尺寸。
- **B. 字面量 + 拔分支**：改常量数值，或把条件跳转换成 `NOP`（`00bf`）。
- **C. 代码钩子**（最强）：把函数开头若干字节换成 4 字节远跳 `004b1847 + addr|1`，
  跳到模块尾部追加的 Thumb 代码，执行完再跳回。Z30 的 `long_exposure` 是范例。

### 7.3 容量

模块尾部可追加代码，但总长受"模块区容量"限制。Z30 实测 `CAPACITY = 0x2940000`（43,253,760），
stock 33,939,514，剩余约 9.3 MB。

**Z6 的容量尚未测出。** 本项目的画幅补丁纯等长编辑、不追加代码，因此不依赖容量。

### 7.4 为什么整包签名被绕开

原厂整包头部有 `header[0:20] == SHA1(decrypted_body ‖ K8)` 的键控摘要，`K8` 逐机型。
Z8/Z9 的 `K8` 已被公开研究解出，**Z6/Z7 尚未**。

但上游的投递方式是**独立 EG 模块**（Z30：`EG209020.BIN`；Z7：`EG161080.BIN`），
不是重打包整包——模块级只需 CRC，因此不需要 `K8`。

> ⚠️ **这个前提尚未在 Z6 上验证**，是第 9 章通道探路的唯一目的。

## 10. 快门声音（调查中）

已掌握的事实：

- 事件名表在 `0x1E8F930`：`AFAssistLight` / `ShutterDrive` / `Beep` / `Key` / `ChangeLV`
- 有 beep 播放 API，错误串 `BeepPlay failed` / `BeepPlay was timeout`
- EG 内嵌两个 RIFF：一个是无尺寸的 WAV 写出模板（配合 `A:\TEST%04d.WAV` 调试录音），
  另一个是完整的 48 kHz 立体声 16 bit、约 60 秒的音频资源
- 相关源码模块：`AudioApplicationService.c`、`AudioApplicationServiceBeep.c`、`AudioApplicationServiceMovieRec.c`

待定：Z6 的"快门声音"究竟走蜂鸣器还是走音频通路；`ShutterDrive` 是机械驱动事件还是发声事件。

**决策门**：若只有 beep 通路 → 做低风险的波形/事件替换；若需新增音频链路 → 记为暂不可行。

## 11. 风险

| 风险 | 等级 | 说明 |
|---|---|---|
| Z6 不接受独立 EG 文件 | 中 | 一次点菜单即可知道，代价极小 |

| 内嵌预览拉伸 | 高 | 需同步修预览尺寸 |
| 追加代码越界 | 中 | 容量未知 |
| 更新中变砖 | 低但不可逆 | 电量、不断电；先刷一次官方原版验证通道 |

**回滚**：`_dec/EG162080.BIN`（原厂模块）+ `Z_6_0380.bin`（原厂整包）始终保留。

## 12. 通道探路（先做这个，再谈任何上机）

```powershell
& $py -m z6fw probe
```

生成 `build/EG162080-PROBE.BIN`：与原厂 EG **仅差 1 个字节**（位于一段零填充中间），
因此 CRC 失配（residue `0x2293` 而非 0），尺寸完全不变。

放卡 → 菜单「设定菜单 → 固件版本 → 更新」，观察相机反应：

| 反应 | 结论 | 下一步 |
|---|---|---|
| "固件文件不正确 / 损坏" | ✅ 相机确实在读 EG 文件，且校验早于写入 | 通道成立，可继续 Phase 2 |
| "找不到固件" / 无反应 | ❌ 通道不通 | **停止**，只交付文档 |
| 真的开始安装 | ⚠️ 不校验 CRC，风险过高 | 立即断电退卡，放弃该路线 |

## 13. 术语

| 术语 | 含义 |
|---|---|
| EG | Engine，机身主程序模块 |
| ExMCU | External MCU，外部控制单片机 |
| VR | Vibration Reduction，机身防抖 |
| scatter | 启动时把 ROM 数据搬到 RAM 的搬移表 |
| residue | 数据连同自身 CRC 一起计算得到的结果；合法时为 0 |
| inline hook | 把函数开头改成跳转，跳到自己的代码再跳回 |
| aspect_id | 尺寸表里标识画幅的编号（0=3:2，3=1:1，4=16:9） |

## 14. 给后来者的三句话

1. **不要从"高熵 = 强加密"开始推理。** 用跨版本同一位置的相同率来判断。
2. **不要急着全量反编译。** 33.5 MB ≈ 14 万函数；你需要的是"能回答某个具体问题的索引"。
3. **真正的门槛不是破解，是投递与恢复。** 在通道验证和恢复路径确认之前，一切补丁都只是纸上作业。
