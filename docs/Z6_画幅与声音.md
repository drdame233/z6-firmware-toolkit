> 本文记录目标 2（21:9 与 Max32 画幅）和目标 3（快门声音）的实现状态与结论。

## 一、画幅（目标 2）

### 1.1 目标尺寸

计算规则：`高 = 量化到 4 的倍数(该档原厂宽度 / 目标比例)`；宽度沿用原厂值。

| 预设 | 比例 | L | M | S |
|---|---|---|---|---|
| `aspect-21x9` | 7/3 = 2.3333 | **6048×2592** | 4528×1940 | 3024×1296 |
| `aspect-max32` | 6048/4000 = 1.512 | **6048×4000** | 4528×2996 | 3024×2000 |

- Max32 的 L 档两条边均可被 32 整除：`6048/32 = 189`、`4000/32 = 125` ✅
- 21:9 的 L 档同样满足：`2592/32 = 81` ✅
- 两者都复用原厂 **16:9 槽位**（`aspect_id = 4`，机身内部 area 2），因此菜单仍显示"16:9"。

### 1.2 已实现（可构建、结构自检通过）

```powershell
& $py -m z6fw aspect --preset aspect-21x9
& $py -m z6fw aspect --preset aspect-max32
```

每个预设 **3 处等长编辑、共 6 字节**，全部落在 `0x1065FDD0` 尺寸表的 16:9 三条记录的高度字段：

| 预设 | L 高 | M 高 | S 高 |
|---|---|---|---|
| stock | `0x0D48` (3400) | `0x09F0` (2544) | `0x06A0` (1696) |
| 21:9 | `0x0A20` (2592) | `0x0794` (1940) | `0x0510` (1296) |
| Max32 | `0x0FA0` (4000) | `0x0BB4` (2996) | `0x07D0` (2000) |

校验项：模块 CRC residue = 0、版本串存在、scatter 指纹正确、尺寸表回读一致、aspect_id 仍为 4、
4 像素量化、未越出传感器、**字节级 diff 恰好等于声明改动的 2 倍字节数**。

### 1.3 阻断项：裁切窗口未改 ⚠️

**当前候选不可上机。** 原因：

出图尺寸表是"结果尺寸"，但决定"拍哪一块传感器"的窗口不在表里。
反编译 `0x103C2FB8` 段看到裁切矩形是**算出来的**：

```c
psVar3 = (short *)(*in_r2 + (short)in_r2[10] * 0x14);   // 步长 0x14 的表，含 (w,h)
x = in_r2[1]           - *psVar3   / 2;                 // 中心 - w/2
y = *(short*)(in_r2+6) - psVar3[1] / 2;                 // 中心 - h/2
```

而所有"原始窗口"字面量搜索全部 0 命中：

```
(0, 312, 6048, 3400)  (312, 3400)  (1012, 0, 4024, 4024)  (1056, 700, 3936, 2624)
```

**因此：只改尺寸表 → 相机把现有 16:9 窗口重采样到新高度 → 画面被压扁，而不是裁切。**

上游 Z30 项目正是踩过这个坑：v2「机内预览被纵向拉长」，v8 的"成片成功"结论被复测推翻，
到 v42/v43 才稳定，历经 40 多个版本。

### 1.4 下一步（唯一阻断项的解法）

1. 从 `0x103C2FB8`–`0x103C3460` 完整反编译，找到把 aspect 选择映射为传感器窗口的代码；
2. 判定该处是常量、查表还是计算：
   - 若是常量/查表 → 继续等长替换；
   - 若是计算 → 采用 Z30 的 inline hook：把函数入口改成 `004b1847 + addr|1` 远跳，
     跳到模块尾部追加的 Thumb 代码，按新比例返回窗口，再跳回。
3. 同步修**内嵌预览尺寸**（Z30 的 `640×236 / 1920×708` 就是干这个的），否则机内回放拉伸。
4. 之后才允许上机，且先只验证 L 档。

## 二、快门声音（目标 3）

### 2.1 调查到的事实（✅ 实测）

| 项目 | 位置 / 内容 |
|---|---|
| 音频事件名 | `AFAssistLight` / `ShutterDrive` / `Beep` / `Key` / `ChangeLV`（文件偏移 `0x1E8F990` 附近） |
| 该表的代码引用 | **0 处**（在 `0x11EAF910`–`0x11EAF9B0` 范围内逐个地址搜索字面量均无命中）→ 由数据表间接引用，非代码直接寻址 |
| beep API | `BeepPlay`（字符串位于 `0x5046F4` / `0x504708`），错误串 `BeepPlay failed`、`BeepPlay was timeout` |
| 声音服务 | `CSoundService`（`0x1F72607`）、`SoundEv`（`0x0F1E68`） |
| 内嵌音频资源 | `0x14A64F4`：合法 WAV，48 kHz / 立体声 / 16 bit / 60 秒 / 11.52 MB；**全模块仅 1 处引用**，在 `0x1006C668` |
| 该引用的邻接内容 | 同一字面量池紧邻 `A:\TEST%04d.WAV` 与 `A:\TEST%04d.aac` → 属调试录音/播放路径 |
| WAV 写出模板 | `0x4DB84`：`RIFF`+`WAVE`+`fmt `+`data` 但**无尺寸字段**，典型的运行时回填模板 |
| 相关源码模块 | `AudioApplicationService.c` / `AudioApplicationServiceBeep.c` / `AudioApplicationServiceMovieRec.c` |

### 2.2 结论（已按先例更正）

**早前的判断有误，在此更正。** 最初的结论是"Z6 无 SD 播放通路，故不可行"。
那只对**原厂固件**成立。公开先例证明可行：

> [`WonderLantern/WonderLantern-z6`](https://github.com/WonderLantern/WonderLantern-z6)
> 「Nikon Z6 长曝光与肩屏倒计时 v1 — 适用机型仅为 Nikon Z6，基于 C3.80」
> 「本版包含自定义快门声，将肩屏倒计时主体迁入**卡载 `SLOWCORE.BIN`**」

**这是针对同一份 C3.80 固件的公开实现。** 因此目标 3 的定性应为：

| 问题 | 结论 |
|---|---|
| 能不能做 | **能**，同版本已有先例 |
| 原厂固件里有现成通路吗 | 没有——必须先由补丁建立 |
| 靠什么实现 | 补丁注入 + **卡载二进制**（`SLOWCORE.BIN`），不是改几个字节 |
| 工作量 | 相当于自建一条"音频播放 + SD 读取 + 快门事件挂钩"的链路 |
| 已知未完成项 | 先例自述："声音菜单的触摸操作尚未修好；机械快门下，快门倒计时不可用" |

对原厂固件的观察仍然有效，且正是"为什么必须自建"的原因：

1. 现有音频资源是编译进 ROM 的常量，不是从 SD 卡读取；
2. `A:\TEST%04d.WAV` 是调试录音的**写出**路径，不是播放输入；
3. Z6 的快门声主要是机械声（反光板/快门帘），电子发声只有固定音调的蜂鸣器（beep）。

**本项目本轮不实现**，理由从"不可行"更正为"工程量等同于独立立项"。
计划中的决策门因此改为：**记录结论 + 指向先例**，而不是判定不可行。
