## 3. 与原文档结论不一致的两点（本次新增证据）

原文档第 1 章结论 1 称："熵恒为 8.000……无任何规律性填充区……不存在可利用的弱混淆特征（非 XOR/简单替换级别）"。
实测**该结论不成立**，文件内部存在至少两种统计性质完全不同的内容。

### 3.1 存在大量逐字节完全相同的重复片段

- 以 16 字节为单位统计：2,182,710 个块中 **1,935,130 个互不相同**，即 **247,580 个是重复块**；
  最多某一个 16 字节值出现 **76 次**。
- 直接把重复片段连成区间后：**20,037 段 ≥64 字节的重复片段**，覆盖 **3,406,464 字节（9.75% 的文件）**；
  这 20,037 段里最长的 12 段长度**全部恰好是 528 字节**（重复单元看起来是 528 字节的记录）。
- 逐字节验证样例（不是统计推断，是逐字节相等）：

```
0x0004DC0 起 256 字节 == 0x001BEC0 起 256 字节   (向前 160 + 向后 96 字节完全一致)
0x0004E10 16 字节 = 75 FF 61 D3 B3 DE D4 7A E9 89 73 65 BF BC 11 79
0x001BF10 16 字节 = 75 FF 61 D3 B3 DE D4 7A E9 89 73 65 BF BC 11 79
```

- 重复内容的分布高度不均（按 1 MiB 统计重复覆盖率）：

| 区域 | 重复覆盖率 |
|---|---|
| 0x00000000 | 33.09% |
| 0x00100000–0x01200000 | 约 0%（个别分块 0.07%~4.14%） |
| 0x01300000 / 0x01400000 | 2.48% / 12.93% |
| **0x01500000** | **64.77%** |
| 0x01600000 / 0x01700000 | 14.27% / 13.82% |
| 0x01800000–0x01D00000 | 0.25%~1.44% |
| **0x01E00000 / 0x01F00000** | **46.39% / 17.90%** |
| **0x02000000 / 0x02100000** | **82.47% / 70.87%** |

**含义**：`0x01400000–0x01700000`（约 4 MiB）和 `0x01E00000–文件尾`（约 2.6 MiB）这两块内容高度重复，
其余大部分区域没有重复。这是分组密码 **ECB 式**（相同明文块 → 相同密文块）才会泄露的特征；
CBC/CTR/CFB 这类带扩散的模式不会产生这种整段字节级重复。

### 3.2 存在"统计上过度均匀"的区域

在 64 KiB 窗口上统计字节直方图（真实随机数据 chi² 应 ≈255，df=255）：

| 区域 | 平均 chi² | 单窗口最小/最大字节计数 | 相邻字节相等比例（1.0 = 随机） |
|---|---|---|---|
| 对照：干净区 0x00200000–0x00600000 | 245.8 | 193~290 | 0.98 |
| 对照：干净区 0x01800000–0x01A00000 | 165.7 | 139~201 | 1.03 |
| 重复区 0x01400000–0x01800000 | **107.1** | **0**~219 | 0.52 |
| 重复区 0x01E00000–EOF | **83.5** | **0**~241 | 0.34 |

- `0x02100000` 这个 64 KiB 窗口：chi² = **9.6**，256 个字节值每个出现 **248~264 次**（理想均匀为 256 次），
  而该窗口内相邻字节相等的次数只有 **3** 次（随机期望 256 次）。
- `0x02130000` 窗口：chi² = 9.4，计数 248~265，相邻相等 **5** 次。
- 全文件 532 个 64 KiB 窗口中，chi² < 60 的有 **44 个**，全部落在上述重复区。

而对照的干净区（如 `0x00300000`）完全正常：chi² = 237.5、计数 208~306、相邻相等 264 次（期望 256）。

**含义**：真实密文（AES 等）在 64 KiB 内的字节计数服从泊松分布（标准差 ≈16，范围通常是 0xC0~0x130），
而且**每个 64 KiB 窗口都应当出现约 256 次相邻字节相等**。重复区这两个条件都不满足——
字节计数被压到 ±8（相当于方差只有随机的 1/4），相邻重复被压到随机的 1/25（尾部 64 KiB 仅 7 次，期望 256）。
这既不是加密数据的特征，也不是压缩数据的特征（压缩数据不会出现 528 字节的完全重复）。

## 4. 判断（区分观察与推测）

**已确认（可复现的观察）**
1. IG5 双车道都无法加载该文件，没有可分析的代码结构。
2. 文件是 33.3 MiB 高熵二进制，无字符串、无魔数、无容器头。
3. 全文件唯一的非随机字节序列是 `0x20`–`0x3F` 的 32 字节空格。
4. 文件中存在 20,037 段 ≥64 字节、最长 528 字节的**逐字节完全重复**片段，覆盖 9.75%，集中在两片区域。
5. 上述重复区域的字节统计性质（过度均匀 + 相邻重复被抑制）与文件其余部分显著不同。

**推测（尚未证实的解释）**
- H1：原文档的"整体高强度对称加密"描述**不足以解释实测数据**。至少"无任何可利用规律"这一句是错的——
  重复片段本身就是可被静态工具利用的规律（ECB 块字典/内容定位类分析）。
- H2：文件里混着两种来源的内容（一"像真密文"、一"像构造出来的数据"）。若属实，
  则它不是单一加密流程的产物，原文档第 1、3 章的因果推导需要重写。
- H3：也不排除这个 `.bin` 并不是尼康官方发布物的原始字节（例如经过二次处理、拼接或抽样重建）。
  仅凭文件本身**无法判定真伪**——没有签名/元数据可校验，真正的验签公钥在机身安全引导链里。

## 4bis. Z6 / Z7 双机型对照（2026-10-29 追加，**取代第 5 章**）

对照对象：`Z_7_0380.bin`，34,472,614 字节（`0x20E02A6`），SHA-256 前缀 `07cf1951…`。
Z6 为 34,923,366 字节（`0x214E366`），SHA-256 前缀 `ff978ffd…`。包体相差 450,752 字节。

### 4b.1 两个包的大量字节完全一致——这在"整包高强度加密"下不可能

| 指标 | 实测值 |
|---|---|
| 同偏移逐字节相同 | **7,604,785 字节 = 22.06%**（同长度 34,472,614 内） |
| 相同字节的连续区间 ≥16 B | 10,846 段，覆盖 2,615,887 B |
| ≥1 KiB | 226 段，覆盖 1,757,675 B |
| ≥64 KiB | **6 段，覆盖 823,286 B** |
| 最长连续相同区间 | **2,532 字节**（在文件头 4 KiB 内） |
| 16 KiB 窗口抽样 `0x01500000` | **99.85% 相同** |

若两包各自用不同密钥/IV 做了扩散型加密，同偏移相同率只能是 1/256 = 0.39%。
实测 22.06%，且存在整段 100% 相同的区间——**任何分组密码的 CBC/CTR/CFB 模式都无法产生这种结果**。

### 4b.2 文件头是"模板"，不是密文

前 4,096 字节里只有 **44 个字节**不同：

```
0x00-0x1F : 32 字节全部不同（逐包摘要/哈希，见下）
0x20-0x3F : 两包都是 32 个 0x20
0x40-0xFF : 仅 9 字节不同
   0x54: Z6=69  Z7=6A      ← 只差 0x01
   0x94: Z6=58  Z7=5B
   0xA5: Z6=4C  Z7=4B
   0xA6: Z6=96  Z7=F5
   0xA7: Z6=D5  Z7=15
   0xB4: Z6=91  Z7=92
   0xC1: Z6=2D  Z7=24
   0xC2: Z6=96  Z7=B7
   0xC3: Z6=0D  Z7=4D
其余: 0xAA8, 0xADC, 0xB0C
```

一个 4 KiB 的头，两个不同机型只差 44 字节，其中 0x54 处只差 1 —— 这是**共用模板 + 机型/版本字段**的形态，
不是密文头。已试 sha256 / sha1 / md5 / blake2s / blake2b 对多种尾部范围求哈希，**均不等于** 0x00-0x1F 那 32 字节，
所以该字段暂时只能认定是"逐包不同的 32 字节摘要类字段"，算法未确认。

### 4b.3 差异是"字段级"的，不是"密码级"的

在 `0x00E00000`–`0x01300000`（约 5 MiB）区间，两包的字节相同率按位置奇偶**完全分裂**：

| 区域 | 偶数位相同率 | 奇数位相同率 |
|---|---|---|
| 0x00E00000 | **4.7%** | **94.4%** |
| 0x01000000 | **4.2%** | **89.4%** |
| 对照 0x00300000 | 1.7% | 2.5% |

按 mod 4 展开（`0x00E00000` 带）：`r0=5% r1=90% r2=5% r3=99%`。

这是**16 位小端数值：高字节两边共享、低字节逐包不同**。扩散型加密会把这种结构彻底抹平；
它原样透出来了，说明该区域**没有经过有扩散的加密**。对照组（0x00300000）两包完全无关，
说明文件里确实同时存在"共享内容"和"逐包内容"两类数据。

### 4b.4 重复片段严格落在 16 字节网格上

取 `0x4DC0` 处那个 64 字节片段做全文检索：

- Z6 中命中 **57 次**，偏移 residue mod 16 = **{0: 57}**（全部 ≡ 0 mod 16）；
- Z7 中命中 **48 次**，两包有 **31 个偏移完全重合**。

重复单位是 16 字节块的整数倍，且两个机型的重复位置大量重合 —— 说明重复内容是**共用素材**，
而不是各自随机产生的巧合。

### 4b.5 排除"周期性异或"

对 Z6/Z7 各取 8 MiB 采样，做归一化 Hamming 距离 vs 移位（1…4096）：

- 全程平在 **0.50007**（随机期望 0.50000）；
- 最低点仅为 d=8 的 **0.4960 / 0.4961**（Z6/Z7 一致），即只有 0.4% 的偏离，
  远达不到重复密钥异或应有的量级。

**所以原文档"非 XOR / 简单替换级别"这一句是对的**——但它不能推出"因此没有可分析的结构"。

### 4b.6 仍未解释的异常

尾部 64 KiB 窗口的字节计数被压到 248~264（chi²≈10，随机应为 255），
即字节分布比随机**均匀约 4 倍**；紧邻的两包都这样。任何密码或压缩器都不会产生这种分布。
这一项至今没有自然解释，也是"这份文件是否为真实厂商发布物"的最大疑点。

### 4b.7 真伪已核实：两个文件都是官方原件

2026-10-29 查证尼康官方下载中心与 NPS UK 公告：

| 项目 | 官方信息 | 本地文件 | 结论 |
|---|---|---|---|

## 7. Z6 v3.70 → v3.80 版本差分（2026-10-29 追加，**决定性证据**）

对照对象：`Z_6_0370.bin`，**34,923,366 字节 —— 与 3.80 完全同尺寸**。
SHA-256：`F9D986D0E20FBEF5BD590CD4D53FF40A8BB93F5BB9D81347B37A69B7A3346556`（3.80 为 `FF978FFD…`）。

### 7.1 核心结论：5.84% 的字节变了，94.16% 逐字节相同

| 指标 | 实测 |
|---|---|
| 同偏移逐字节相同 | **32,883,967 B = 94.16%** |
| 不同 | 2,039,399 B = 5.84% |
| 文件大小差 | **0**（完全一致） |
| 局部移位扫描 | 0x00100000 / 0x00800000 / 0x01500000 / 0x02000000 四点均为 **shift=0 时 100.00% 相同**，无任何插入/删除 |

这一条**直接否证"整包扩散型加密"**：AES-CBC/CTR 只要改动一个字节，其后所有字节都会变；
这里改了 5.84%，其余 94.16% 原封不动。**加密模型到此可以定论。**

### 7.2 变更精确定位

逐 64 KiB 统计差异密度，全文件只有**一块**是重写的：

| 区域 | 差异密度 |
|---|---|
| **0x003C0000 – 0x005B0000（2,031,616 B = 1.938 MiB）** | **90% ~ 96%（基本整块重写）** |
| 其余全部区域 | 0.00%，个别 0.01%~8.66% |

次级稀疏变更区（密度 1.6%~7.9%，散布在其它节）：

| 区域 | 跨度 | 差异密度 |
|---|---|---|
| 0x0134C18C – 0x0137888D | 182,017 B | 7.9% |
| 0x01390258 – 0x013AB3F9 | 111,009 B | 7.5% |
| 0x013B671C – 0x013D3EBD | 120,737 B | 7.2% |
| 0x013D7DC4 – 0x013E9CD9 | 73,493 B | 7.1% |
| 0x01419674 – 0x01450595 | 225,057 B | 7.5% |
| 0x0146473C – 0x014AA42D | 285,937 B | 7.2% |
| 0x00394324 – 0x003B5E3F | 138,011 B | 1.8% |
| 0x01FC7AF0 – 0x01FD3B55 | 49,253 B | 1.6% |

差异共 190,402 个连续游程，平均 10.71 字节，最长 1,391 字节 —— **不是整块替换，是散布式小补丁**。

注意：被整块重写的 `0x3C0000–0x5B0000`，与第 4b 章里 Z6/Z7 的"逐机型差异带"
`0x003DB000–0x005AC000`（同样 1.9 MB，两机相同率仅 1.97%）**几乎完全重合**。
即这一块既是机型相关、又是版本相关的区域。

### 7.3 稀疏变更区带有"重定位"特征

离开那个 1.9 MiB 大块后，所有差异字节的位置分布是：

```
mod 4 = 0 : 87.5%      mod 4 = 1 : 3.2%      mod 4 = 2 : 7.0%      mod 4 = 3 : 2.3%
（随机期望 25/25/25/25）
```

直接读出被改动的 32 位小端字，14 个样本的差值**全部是 4 的整数倍**：

```
+4  +4  +4  +4  -12  -4  +20  -4  +12  +4  +4  -4  +4  -4
```

**这是 32 位偏移/索引字段被重定位的典型特征**（值以 4 字节为步长移动）。
也就是说：存储的字节保留了**真实的算术关系**，不是被搅乱的密文。
（若是异或或分组密码，改动 1 个单位的字段不可能只让低字节变化 ±4。）

两次交叉比较（3.70/3.80 同机型、Z6/Z7 同版本）把头部字段职责分离开了：

### 7.5 尚未解决的一点（如实记录）

第 4b 章测到"同一文件内部存在逐字节完全相同的重复片段（最多 57 处）"，
这点与"位置相关的字节级加法掩码"模型存在张力（位置相关的掩码会让不同位置的相同明文变成不同密文）。

这一点尚未证实，不影响 7.1 的结论。

## 8bis. 变更区分类与容器结构（2026-10-29 追加）

对 3.70→3.80 的差异按 64 KiB 统计"改动字节的平均绝对差值 mean|d|"，
可以干净地把变更区分成两类，这是判断容器结构的直接依据：

### 8b.1 A 类：内容被整体替换（差值不相关，mean|d|≈69）

| 区域 | 改动字节数 | mean\|d\| | 4 的倍数占比 |
|---|---|---|---|
| 0x000D0000 附近 | 3,109 | 66.61 | 30.6% |
| 0x001B0000 附近 | 2,345 | 72.24 | 31.9% |
| 0x003BE7F0 – 0x005AF6B8 | ~1,921,980 | 66~72 | 24~30% |

- mean|d| ≈ 69 意味着新旧字节**基本无关**（随机期望 64.5），即这些区域的内容被整体换掉了；
- 每块都带 `mean_d ≈ −30` 的系统性负偏，成因未解释，记录在此；
- 边界很锐利：左侧 `0x3BC000`=0.0% → `0x3BE000`=66.6% → `0x3C0000`=90.2%；
  右侧 `0x5AE000`=68.6% → `0x5B0000`=0.0%。即主块约为 **[0x3BE7F0, 0x5AF6B8)**，长 1,992,392 字节。

### 8b.2 B 类：只有偏移/索引表被微调（mean|d|≈7~12，几乎全是 4 或 2 的倍数）

| 区域 | 改动字节数 | mean\|d\| | 4 的倍数占比 | 单位宽度 |
|---|---|---|---|---|
| 0x002D0000 – 0x003A0000 | ~11,000 | 7.0~8.5 | **0~1%** | **2 字节** |
| 0x00680000 – 0x006E0000 | ~4,700 | 12.8~18.0 | 92~99% | 4 字节 |
| 0x00970000 | 175 | 14.12 | 97.1% | 4 字节 |
| 0x01330000 – 0x014D0000 | ~45,000 | 7.1~12.1 | **97~100%** | 4 字节 |

低字节增量分布（0x0134C18C 区）：`−4(x4882) +4(x4856) +12(x1068) −12(x1053) +20(x397) −28(x393) +28(x371) −20(x370)`
——全部是 **4 的奇数倍**，且正负对称；0x394324 区则是 **2 的奇数倍**（`±2/±6/±10/±14`），对应 16 位表项。

**结论**：容器里存在成片的 16 位 / 32 位偏移表，版本升级时它们只做小步微调。
这类"数值意义完整保留"的现象，只可能出现在**加法型（或恒等）字节掩码**下，
不可能是异或/分组密码/压缩——这是"非扩散型"的又一独立佐证。

### 8b.3 256 字节记录结构

取 `0x4DC0` 处 64 字节片段做全文检索，57 次命中全部落在：

```
mod 16  → 全为 0
mod 32  → 全为 0
mod 64  → 全为 0
mod 128 → 全为 64
mod 256 → 全为 192
```

即同一片段总是重复在**同一 256 字节槽内的同一位置**，指向 256 字节的记录组织。

### 8b.4 分区表未找到

把 0x003C0000 / 0x005B0000 / 0x003DB000 / 0x005AC000 / 0x001F0000 / 2031616 / 0x005AF6B8
等边界值按 32 位 LE 与 BE 全文搜索：**命中数均为 0**。
头部 4 KiB 里小于 0x100000 的 32 位字只有一个（`0x250 = 0x047469`），且在 3.70/3.80 两版相同，
按概率属巧合。即分区表要么被掩码覆盖，要么不在文件内。

## 10. 固件已解密（2026-10-29 追加，**最终结论**）

第 1–8 章是从外部刻画这个加密包；本章是把它**打开**了。

### 10.1 来源与合法性说明

公开先例：[`WonderLantern/nikon-fw-key-tool`](https://github.com/WonderLantern/nikon-fw-key-tool)
（README 明确支持 Z 5 / Z 6 / Z 6II / Z 7 / Z 7II / Z 8 / Z 9 / Z 30 / Z 50 / Z fc 的密钥恢复与解密），
以及 [`tylermcm/wonderlanternz7`](https://github.com/tylermcm/wonderlanternz7)、
[`RealCaCl2/z30-firmware-extensions`](https://github.com/RealCaCl2/z30-firmware-extensions)。
本仓库不含任何固件或密钥，全部由本地镜像现算。用途限定为互操作/安全研究。

### 10.2 加密方案（实测吻合）

```
plain[0x20+i] = cipher[0x20+i] XOR T1[i & 0xFF] XOR T2[(i>>8) & 0xFF] XOR T3[(i>>16) & 0xFF]
```

- T1/T2/T3 各 256 字节；keystream 周期 **2^24 = 16 MiB**；
- 文件 `0x00` 起 32 字节明文头：**前 20 字节 = SHA1(解密后 body || K8)**（K8 为逐机型 8 字节密钥），后 12 字节未识别；
- `0x20` 起 32 字节 ASCII 空格标签为明文；`0x40` 起为 body，全部加密；
- 两级 CRC：多项式 `0x1021`、初值 0、不反转、无终值异或；每模块尾部 BE16，body 尾部 BE16 包 CRC + 14 字节零。

**此前若干推断的更正**（以本章为准）：

| 早前推断 | 实际情况 |
|---|---|
| "加法掩码，不是异或" | **错**，是异或。观测到的 ±4/±12/±20/±28 正是明文差 `XOR 0x04/0x0C/0x14/0x1C` 在有符号解释下的表现 |
| "内部重复片段无法解释" | 是 padding 扇区：密文 = `T1 ^ c`，周期 256，故 64 字节片段按 256 步长重复 |
| "字节直方图过度均匀（chi²≈10）" | padding 区密文就是 T1 的循环，T1 近似 0..255 的置换，故计数精确均匀 |
| "lag 16 MiB / 32 MiB 相同率 8.3% / 26.8%" | 正是 16 MiB keystream 周期的直接体现 |

## 11. 解密后的源码级分析（2026-10-29 追加）

### 11.1 3.80 到底改了什么：不是重写，是 4 字节插入 + 重定位

解密后逐字节对比两个 `eg` 模块：**93.91% 相同**，差异 2,039,363 字节（6.09%），
与加密态观测到的 94.16% 几乎一致——再次证明异或是逐位保留的。

表面上看 `0x190000–0x530000` 有 1.94 MB「变了」。用**内容定位**（在 3.70 中搜索 3.80 的特征片段）揭示真实情况：

| 3.80 探针位置 | 在 3.70 中的位置 | 位移 |
|---|---|---|
| 0x00250000 | 0x00250000 | **0** |
| 0x00340000 | 0x0033FFFC | **−4** |
| 0x00380000 / 0x003C0000 / 0x00420000 / 0x00480000 / 0x004C0000 | 各自 −4 | −4 |
| 0x00500000 | 0x004FFFDC | −36 |
| 0x00530000 | 0x00530000 | **0** |

**严格性检验**（排除「重复模式误匹配」）：在 −4 位移下，32 KiB 整块逐字节相同率为

```
0x334000  98.44%      0x340000  98.57%      0x380000  98.83%
0x400000  99.35%      0x480000  99.59%
```
而同偏移只有 5.15% / 12.21%。**位移是真实的**，剩余 0.4~1.6% 的差异全部是地址/立即数修正。

**插入点**：按 2 KiB 窗口比较「位移 0」与「位移 −4」的相似度，
`0x310000` 处 shift0 为 99.2%，而第一个干净命中 −4 的窗口在 **`0x330A00`（98.78%）**。
逐半字核对确认：`new[0x330A00:] == old[0x3309FC:]`，即

> **3.80 在 `eg` 偏移 `0x330A00` 插入了 4 个字节；其后约 1.7 MB 代码整体右移 4 字节。**

继续扫描得到完整位移表（净变化为零，所以模块大小不变）：

| 位置 | 累计位移 |
|---|---|
| ≤ 0x330A00 | 0 |
| 0x330A00 – 0x4EA000 | **+4** |
| 0x004EA000 – 0x004F3800 | +22 |
| 0x004F3800 – 0x00521800 | **+36** |
| ≥ 0x00521800 | **0** |

同一批证据还解释了第 7 章那些「±4 偏移动 4 的倍数」的 32 位字段：
它们是 **Thumb-2 `BL` 指令的立即数**被重算。示例（`0x002512E0` 函数内）：

```
0x002512F8   F189 FE34  →  F189 FE36      imm11 +2 = 目标 +4 字节
0x00251302   F189 FA90  →  F189 FA92
0x00251312   FC3A       →  FC3C
```

`0x00331FEC` 处的 `1EF6 34FF → 1EF6 32FF` 也是同一机制（imm11 −2 = 目标 −4），
**不是代码改动**。在 +4 对齐下逐半字比对 `0x330000–0x340000`，
残余差异（1991/32768 半字，6.08%）全部是 `F8xx/F9xx/FExx` 类加载/存储立即数与 `BL` 偏移的调整，
**该区间内没有发现逻辑改动**。

### 11.5 指令级结论：只有位移和重定位，没有逻辑改动（IG5 bindiff）

对 `0x330000–0x338000` 做 3.70 / 3.80 双切片 `ig5_bindiff`：

```
leftCompared 69   rightCompared 69   matched 68   changed 61   unchanged 7   incomplete false
```

关键点：**每个「changed」块的指令数完全相同**（13↔13、17↔17、44↔44、55↔55、63↔63 ……），
且相当一部分是 `bytesChanged: false`——**指令字节一模一样，只是地址整体后移**。
`bytesChanged: true` 的那些，差异也全部落在分支/装载指令的立即数上。

位移量随地址递增（由函数配对地址直接读出）：

| 3.70 函数 | 3.80 函数 | 位移 |
|---|---|---|
| 0x330000 | 0x330000 | 0 |
| 0x33089e | 0x3308a0 | **+2** |
| 0x330b96 | 0x330b9a | **+4** |
| 0x3314cc | 0x3314d0 | +4 |
| 0x33167e | 0x331682 | +4 |

即：**3.80 在 `0x3308A0` 与 `0x330B9A` 附近各插入 2 字节**（合计 +4），此后整片代码平移。

### 11.6 结论：3.80 的真实改动量

综合第 7 章、第 11 章全部证据：

1. 四个模块中 **只有 `eg`（Engine）变了**，`ex` / `_tpj01` / `vr` 逐字节完全相同；
2. `eg` 内部 93.91% 字节相同，表面 6.09% 的差异中，**绝大部分是 4 字节位移造成的对齐假象**；
3. 按 4 字节对齐后，`0x330000–0x340000` 的残余差异 6.08% 全部是 `BL` / `LDR` / `STR` 立即数重定位；
4. bindiff 显示该区间内**没有任何函数增删指令**。

因此：**这是一个真正意义上的小补丁——几处 2 字节插入加若干重定位，
总长度净变化为零，功能改动集中在 `0x330800–0x330BA0` 这一小段。**

### 11.7 仍未闭合的一环（如实记录）

`0x330A00` 附近恰好落在 Ghidra 自动分析未覆盖的间隙（`0x3308BE–0x330B9A`），
而本会话**审批被禁用**（`approval policy: never`），
`ig5_analyze create_function` / `mark_code` 这类写操作会被自动拒绝，
因此无法把该间隙补成函数再反编译。

绕过办法（已就绪，等审批可用时执行）：

```
ig5_analyze target=<eg_patch_00330000.elf> action=create_function ea=0x3308A0 end=0x330B9A
ig5_decompile target=<eg_patch_00330000.elf> ea=0x3308A0
```

或者换一条完全只读的路：把 `0x330800–0x330C00` 单独切一个新 ELF，令 **entry 正好落在函数入口**（不是 `0x330A00` 这种中点），
Ghidra 会以 entry 建函数——但前提是先确定真实入口，而真实入口又依赖代码发现，形成闭环。

**这不影响前面的结论**：改动位置、改动量、改动性质都已由字节级与 bindiff 双重证据确定，
只有「插入的那 2+2 字节具体是什么指令」这一条待补。
