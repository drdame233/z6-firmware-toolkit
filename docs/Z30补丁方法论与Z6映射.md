# Wonder Lantern Z30 补丁方法拆解 · 与 Z6 映射

> 目的：吃透"改尼康 Z 系固件"的具体手法，并判断哪些能直接迁移到 Z6。
> 材料：`_repo/wonder-lantern-z30-main`（Z30，EXPEED 6）、`_repo/WonderLanternZ7-main`（Z7）
> 本文只做静态分析与映射，**不含任何刷机动作**。

---

## 0. 一句话总结

Z30 那套做法不是"重新打包签名固件"，而是：

> **在解密出来的 EG 模块里，改数据表项 / 改字面量 / 挂钩子；
> 每一次改动都必须等长、必须匹配原字节；可选地在模块尾部追加汇编代码；
> 最后重算 2 字节 CRC，输出一个独立的 `EGxxxxxx.BIN`，放卡给相机更新器。**

关键点：**整包签名（SHA1(body‖K8)）被绕开了——因为投递的是模块级文件，不是整包。**

---

## 1. 制作链路

```
官方 Z_30_0120.bin
   │  ① container：解密 → 取出 EG 模块 → 校验模块 CRC + 包 CRC + EG 身份
   ▼
stock EG 模块（33.9 MB，CRC residue == 0）
   │  ② plan：features 逐条登记 —— edit(offset, replacement, name, expected)
   │                                  alloc(追加代码) → 返回地址
   ▼
   │  ③ apply_patch：等长校验 → 逐字节校验 → 追加代码 → 重算 CRC → 自检
   ▼
EG209020.BIN  +  EG209020.json（记录每处改动的偏移/原名/原字节/新字节）
```

产物是**模块**，不是完整更新包。文档原话：
"Standalone EG module; **not** a repackaged `Z_30_0120.bin`."

---

## 2. 工具强制的六条硬约束

看 `src/z30_extensions/patch.py` 的实现，以下每一条都是 fail-closed：

| # | 约束 | 代码行为 |
|---|---|---|
| 1 | **源必须完全匹配** | `sha256(source) != expected_sha256` → 直接报错 |
| 2 | **源 CRC 必须有效** | `crc_hqx(source, 0)` 非零 → 报错 |
| 3 | **改动必须等长** | `len(expected) != len(replacement)` → 报错 |
| 4 | **必须匹配原字节** | `source[off:off+len] != expected` → `Expected bytes mismatch at 0x...` |
| 5 | **不得重叠、不得越界** | `edit.offset < end` 或越过 `len(source)-2` → 报错 |
| 6 | **追加代码 4 字节对齐 + 不超容量** | `start % 4` 或 `start+len(append) > capacity` → 报错 |

最后重算 CRC 并**自检 residue 必须为 0**，否则拒绝输出。

这三条设计（等长、校验原字节、重算 CRC）的意义是：**改错了立刻在本地炸掉，不会产出一个"看起来正常但已损坏"的模块**。

## 3. 补丁的三种形态

### A. 纯数据表项（最简单，风险最低）

`features/wifi_5ghz.py` 全文只有 10 行有效代码：

```python
ENTRY       = 0x114A3810
EXPECTED    = struct.pack('<4sII', b'AA\0\0', 7, 7)
REPLACEMENT = struct.pack('<4siI', b'US\0\0', -1, 7)
```

含义：某个 12 字节的"无线国家配置"表项，把 `国家=AA / 请求值=7 / 备用=7`
改成 `国家=US / 请求值=-1 / 备用=7`。

**这类补丁不改任何代码，只改常量表，出问题的概率最低。**

### B. 字面量 + 条件分支（改限制值）

`features/bitrate_slowmo_uncap.py` 里对慢动作限制的三处改动：

```python
(0x10290428, struct.pack('<I', 1_500_000), 'Slow-motion length limit', struct.pack('<I', 180_000)),
(0x1029023A, bytes.fromhex('00bf'), 'Slow-motion file count',    bytes.fromhex('1ad0')),
(0x102A1FE6, bytes.fromhex('00bf'), 'Slow-motion exFAT single file', bytes.fromhex('59b9')),
```

- 第一处是**改常量**：180000 ms（3 分钟）→ 1500000 ms（25 分钟）
- 后两处是**把条件跳转抹掉**：`1ad0`（`BEQ`）和 `59b9`（`B... `）替换成 `00bf`（Thumb 的 `NOP`）

这是"解锁限制"最直接的形态：**改数值 + 拔掉判断分支**。

### C. 代码钩子（最复杂，功能最强）

`features/long_exposure.py` 演示了如何在不重定位整个程序的前提下插入新逻辑：

```python
GETTER = 0x100F303C            # 原始"是否允许长曝光"的属性读取函数
KEY    = 0x11A3                # 要拦截的属性号
EXPECTED_PREFIX = bytes.fromhex('38b50c4600212160')   # 原函数开头 8 字节
```

做法分三步：

1. **写一段新 Thumb 代码**（用自带的 `thumb.py` 汇编器生成）：
   读入参数 → 比较属性号是否为 `0x11A3` → 是则返回"已启用" → 否则跳回原函数继续
2. **在模块尾部追加这段代码**，用 `plan.alloc()` 拿到它的真实地址
3. **把原函数开头 8 字节换成一条 4 字节远跳**：
   ```
   00 4b 18 47  <四字节地址>      ; ldr r3,[pc,#0] / bx r3  → 跳到新代码
   ```

这就是典型的 **inline hook**，而且巧妙地利用了"模块尾部有预留空闲空间"这一点——**不需要重定位任何已有代码**。

## 4. Z30 的地址簿（关键数据）

来自 `src/z30_extensions/platform/z30_120.py`：

| 项目 | Z30 值 | 说明 |
|---|---|---|
| `BASE` | `0x10020000` | **EG 模块加载基址** |
| `STOCK_SIZE` | 33,939,514 | stock 模块大小（含 2 字节 CRC） |
| `CAPACITY` | `0x2940000`（43,253,760） | 模块区容量 → **尾部约 9.3 MB 空闲** |
| scatter 描述符 | 位于模块偏移 `0x14000` | 格式 `(源地址, 目标RAM, 长度, BASE+0x6C)` |

**`CAPACITY > STOCK_SIZE` 是整个方案成立的前提**——有 9 MB 空闲，才能往里追加代码。

已定位的补丁地址：

| 目标 | Z30 地址 | 形态 |
|---|---|---|
| Wi-Fi 国家配置 profile 7 | `0x114A3810` | 数据表（12 字节） |
| 影片码率表 | `0x10713154`（步长 `0x1C`，码率在 `+0x14`/`+0x18`） | 数据表 |
| 慢动作时长常量 | `0x10290428` | u32 字面量 |
| 慢动作文件数分支 | `0x1029023A` | `1ad0 → 00bf` |
| 慢动作 exFAT 分支 | `0x102A1FE6` | `59b9 → 00bf` |
| 长曝光属性 getter | `0x100F303C` | 代码钩子 |
| muxer 125 分钟字面量 | `0x10290408` | 未打（会坏） |

## 5. Z6 映射结果（本文实测）

我拿已解密的 Z6 3.80 做了同样的结构探测，结果如下：

| 项目 | Z30 | **Z6（实测）** | 结论 |
|---|---|---|---|
| 模块加载基址 | `0x10020000` | **`0x10020000`** | ✅ 完全一致 |
| scatter 描述符位置 | 偏移 `0x14000` | **偏移 `0x14000`**，末字 = `0x1002006C` | ✅ 布局一致 |
| scatter 内容 | 3 段 | `(0x11E94DD4→0xC1800000, 0x101400)` 等 3 段 | ✅ |
| stock 模块大小 | 33,939,514 | **33,502,842**（`0x1FF367A`） | 同量级 |
| CRC 机制 | residue 0 | **residue 0** ✅ | 一致 |
| 版本串 | — | `"Ver.03.80.00"` @偏移 0x20 | — |
| **Wi-Fi 国家表** | `0x114A3810` | **`0x11473178`** | ✅ **字节模式完全命中** |
| **影片码率表** | `0x10713154` | **`0x10637370`** | ✅ **结构完全一致** |

### 5.1 Wi-Fi 国家表（Z6 实锤）

Z6 在 `0x11473178` 处有一串 12 字节条目，`AA` + 索引 1..24：

```
0x11473130  41 41 00 00 | 01 00 00 00 | 01 00 00 00     AA / 1 / 1
0x1147313C  41 41 00 00 | 02 00 00 00 | 02 00 00 00     AA / 2 / 2
   ...
0x11473178  41 41 00 00 | 07 00 00 00 | 07 00 00 00     AA / 7 / 7   ← 正是 Z30 改的那条
0x11473184  41 41 00 00 | 08 00 00 00 | 08 00 00 00     AA / 8 / 8
```

Z30 的 `EXPECTED` 是 `41 41 00 00 07 00 00 00 07 00 00 00`，**与 Z6 在 0x11473178 处的 12 字节逐字节相同**。

对应的 Z6 补丁会是这样：

```python
ENTRY       = 0x11473178
EXPECTED    = struct.pack('<4sII', b'AA\0\0', 7, 7)     # 414100000700000007000000
REPLACEMENT = struct.pack('<4siI', b'US\0\0', -1, 7)    # 55530000ffffffff07000000
```

> 🔎 **注意**：结构命中 ≠ 语义等价。Z6 的 profile 7 是否和 Z30 一样对应"未指定地区"的回落，
> 需要实机验证。这一步只是把候选点从 33.5 MB 缩到 12 个字节。

### 5.2 影片码率表（Z6 实锤）

Z6 在 `0x10637370` 处是同样结构的记录表，**步长 `0x1C`，`+0x04` 帧率，`+0x14` 最高码率，`+0x18` 平均码率**（u32，单位 bit/s）：

```
0x10637370  0x08700F00  30000  1001  0  0x000F0001 | 144 Mbps | 120 Mbps    4K 30p HIGH
0x1063738C  0x08700F00  30000  1001  0  0x000F0001 |  72 Mbps |  60 Mbps    4K 30p NORM
0x106373A8  0x08700F00  25000  1000  0  0x000C0001 | 144 Mbps | 120 Mbps    4K 25p HIGH
0x106373C4  0x08700F00  25000  1000  0  0x000C0001 |  72 Mbps |  60 Mbps    4K 25p NORM
0x106373E0  0x08700F00  24000  1001  0  0x000C0001 |  ...                  4K 24p ...
```

这与 Z30 的 `RECORD = 0x1C`、`RATES = 0x14` 完全吻合。

### 5.3 stock 模块已就绪

从解密容器里直接切出的合法模块：

```
文件     : _dec\EG162080.BIN
大小     : 33,502,842 字节
CRC 残留 : 0x0000   ← 与 Z30 的 stock 校验一致
SHA-256  : 1e6348d58750e67372d0a8e363932c57ee9c04d0eb8f62803bcd19812df0d25c
```

> 文件名 `EG162080.BIN` 是按 Z30(`EG209020`)/Z7(`EG161080`) 的规律推的，**未验证**相机是否认这个文件名。

## 6. 血泪教训：能力上限是物理的，不是开关

这段是 `bitrate_slowmo_uncap.py` 注释里的实战记录，**比任何理论都值钱**：

### 6.1 码率不能随便加

> "The encoder keeps maximum kbit / 8 in 16 bits, so stay well below 536 Mbps."

编码器把"最高码率 kbit ÷ 8"存在 **16 位**里，所以理论上限 536 Mbps。作者把上限设成 400 Mbps 留余量。
**这说明码率字段有硬性位宽限制，不是想写多少写多少。**

### 6.2 慢动作时长的真实天花板

> "Stock slow motion stops at 3 minutes... raise the length to 25 minutes."
> "25 minutes is as far as the length can go... they overflow after 32.8 minutes of 30p x4, 31.5 of 25p x4 and 26.3 of 24p x5"

为什么 25 分钟就顶了？因为 **muxer（封装器）的索引表是定长的**：
chunk offset 表和 key frame 表各 **15,750 个条目**，每个 GOP 一条，约 131 分钟素材。
慢动作按回放速度算（4×/5×），实际录制时间只有 1/4~1/5，所以 131 分钟 / 4 ≈ 32 分钟——**这才是真实上限**。

作者实测过越界后果：

| 尝试 | 结果 |
|---|---|
| 时长常量改到 125 分钟 | 录了 4 小时，但 muxer 在自带的 125 分钟字面量处丢弃所有帧，文件断在那 |
| 时长 + muxer 字面量都改 | 生成 162 分钟文件，**无法播放**——索引表溢出，写坏了相邻表 |
| 45 分钟 30p×4（exFAT） | 相机生成 182 分钟文件后**卡死**，key frame 表溢出到 sample description 里 |

要再往上，必须**扩大 muxer 库内部的表**（地址 `0x102CB000-0x102EF000`），而作者明确写：
> "which has not been reverse engineered."

### 6.3 对摄影师的直接含义

**"解锁高码率 / 无限时长"不是改个数字的事。**
你看到的上限（3 分钟慢动作、125 分钟单段）不是尼康随便设的营销限制，
而是**文件格式的索引表容量决定的**。硬突破的结果不是"更长"，是**文件播放不了 / 相机卡死 / 素材丢失**。

这一点比任何"能改什么"都重要。

## 7. Z6 现在到哪一步了

### 已经具备 ✅

| 项目 | 状态 |
|---|---|
| 官方固件解密 | 完成，密钥表已恢复并交叉验证 |
| EG 模块提取（合法、CRC 正确） | 完成，`EG162080.BIN` 已生成 |
| 加载基址 / scatter 映射 | 确认与 Z30 相同（`0x10020000`） |
| 补丁机制（等长 + 校验 + 追加 + CRC） | 完全掌握 |
| 两个数据表地址（Wi-Fi / 码率） | 已定位，字节模式与 Z30 一致 |
| 反汇编/比对工具链 | 可用（IG5 分片 + bindiff） |

### 还没有 ❌

| 项目 | 说明 |
|---|---|
| **任何实机验证** | 一步都没上过机 |
| Z6 的模块区容量 | 未知，决定能追加多少代码 |
| Z6 的 muxer 表地址 | 未定位（能力类补丁必须先有它） |
| Z6 是否接受独立 EG 文件 | **最关键、也最未知的一点** |
| 恢复/救砖路径 | 上游明确写未验证 |

## 8. 建议的推进顺序（按风险从低到高）

1. **只读验证（零风险）**：用 IG5 查 Z6 里那两个表被哪些函数引用，确认它们真的参与对应逻辑，而不是同形的无关数据。
2. **最低风险补丁先做**：Wi-Fi 国家码（纯数据表、不影响成像、出问题只是无线行为异常）。
3. **上机前准备**：原 EG 完整备份、确认更新器行为、确认能否回退。
4. **能力类补丁放最后**：码率/时长涉及 muxer 上限，最容易造成"看起来成功、实际丢素材"。

---

## 9. 一句话收尾

**手法已经吃透了，Z6 的地基也已经打好**——基址、模块、CRC、两个数据表都落到了具体字节。
但**从"定位到字节"到"相机真的接受并正常工作"之间，还隔着一次没人替我们验证过的实机风险**，
而且上游的记录证明这条路踩坏过。

下一步最该做的不是继续改，是**先把风险边界摸清**：Z6 收不收独立 EG 文件、改坏了能不能救回来。
这两个问题不解决，任何补丁都只是纸上作业。
